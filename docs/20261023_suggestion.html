現況盤點 What's Actually There

這一輪不從「想加什麼功能」出發，而是先回答：技能多到 53 個之後，現在的系統架構還撐得住嗎？

1.1 技能生態現況

面向現況觀察
技能總數53（10 個分類）數量已到「需要工具協管」的階段
有週期任務13（watch + onTask）每個技能各自存 state、各自的取消指令
每則訊息都檢查1（auto-reply，any 模式）any 模式只有一個，觸發衝突風險低
助手模式（觸發詞）51觸發詞比對是第一前綴命中即執行，無長度優先
技能熱安裝zip 安裝 + @lw/* 別名自包含外部技能已可自包含分享（2026-10-12）
技能品質資料metrics 有 skill_exec_total{skill,result}有資料、沒有介面；/skills/health 只檢查有定義 health() 的技能

1.2 這次稽核的方法

掃描每個技能的 defaultTrigger 與 triggerAliases，比對「完全相同」與「互為前綴」兩種衝突型態， 再對照 messaging/dispatch.ts 的比對順序（for (const skill of config.skills) → 每個技能獨立比對 → 都命中就都執行）。 這不是推測，是既有程式碼的行為。

三個真 bug Found, Not Hypothesized

Bug ① 觸發詞撞車 → 一則訊息兩個回覆

觸發詞宣佈者使用者輸入實際結果
換算exchange-rate（defaultTrigger）
unit（defaultTrigger）		「阿寶請幫忙 換算 1 km」兩條回覆：一條查匯率、一條轉單位
摘要rss（triggerAliases）
summarize（defaultTrigger）		「阿寶請幫忙 摘要 https://…」兩條回覆：一條讀 RSS、一條摘要網頁
成因：dispatch.ts 對每個技能各自比對觸發詞，命中就執行；技能之間彼此不認識。 兩個技能宣告同一個詞 → 同時命中 → 同時回覆。這在 38 個技能時只是小瑕疵，在 53 個技能、且使用者已經習慣用「換算」「摘要」這類通用詞時，會變成明顯故障。

Bug ② 跨技能別名前綴遮蔽

countdown 的別名是 倒數計時，但 remind 的別名 倒數 更短、且在設定順序中較前。 使用者打「阿寶請幫忙 倒數計時 2026-12-31 跨年」→ 先被 remind 攔走（參數變成「計時 2026-12-31 跨年」）→ 回一段用法提示， countdown 永遠收不到。順序換一下就會好，但那是運氣，不是設計。

Bug ③ 週期任務沒有總入口

13 個技能各自註冊週期任務，狀態存在各自的 watch state，取消也要用各自的指令（公車 取消、rss 退訂…）。 Console 的「排程中的訊息」只顯示一次性訊息排程，不包含技能任務。 使用者想「晚上不要吵我」只能一個一個技能去關。

方向 A：修掉三個 bug P0

P0

最長匹配優先

dispatch 觸發詞比對
比對時收集所有技能的命中，以最長的觸發詞優先；同長度時依設定順序。 如此「倒數計時」會贏過「倒數」，Bug ② 根除；同技能內的長別名也自然優先。
依現況：dispatch 對每技能獨立比對，先到先得。
修好跨技能遮蔽；語意更合理（使用者打了更完整的詞，就該由它接手）。
P0

啟用時衝突偵測

/skills 設定頁
啟用技能時比對所有已啟用技能的觸發詞與別名，發現重疊就在卡片上標示 「換算 與 unit 重複」並提供改名建議。不自動改——自動改觸發詞會讓使用者措手不及。
Bug ① 的兩組重疊即由此浮出來（已在本次稽核中掃出）。
把「雙重回覆」從使用者撞到才知，變成管理員一開就看到。
P0

同長度重複的裁決規則

dispatch 規則
最長匹配只解決「長短」，同長度（換算 vs unit、摘要 vs summarize）仍會兩個都命中。 裁決方式二選一：(a) 只執行設定順序第一個（其餘記錄 log warning）； (b) 全部執行但合併回覆。建議 (a)：語意單純，且能配合 P0 的衝突偵測一起處理。
兩組真實衝突已列於 Bug ① 表格。
雙重回覆消失，且行為可預期、可測試。
P0

迴歸測試護欄

tests/
照前例：抽出純函式 → 真實管線與規則模擬器共用 → 補矩陣測試（相同詞／前綴關係／長別名優先／any 模式不受影響）。 模擬器本來就在做同一套比對，順手就能當第二個驗證點。
2026-10-12 的規則模擬器已建立「單一事實來源」的先例。
改比對邏輯不會靜默壞掉既有行為。

方向 C：統一排程／推播中心 P1

P1

所有技能任務一覽

新頁面 /schedules
列出所有技能的週期任務：技能、對話、頻率、下次執行、上次結果、是否靜音。 資料都在 scheduler（同一套 cron + 持久化），不需要動各技能。
13 個技能都走 ctx.watch() → 同一個 scheduler。
從「要停掉得逐個技能下指令」變成一個頁面看完。
P1

統一靜音時段

全域設定
設一組「勿擾時段」（例如 23:00–07:00），區間內所有技能的推播延後到結束後（而非直接丟棄，避免資訊遺失）。
到價通知、公車到站、颱風警報、每日摘要……目前時段各自為政。
半夜被轟醒這個最常見的抱怨，一次設定全部解決。
P1

單一任務停用／重排

/schedules
直接停用某一條推播（不必打「公車 取消」），或改頻率。底部再給「全部靜音」的大開關。
目前取消路徑分散在各技能的指令裡（公車／rss／holiday／price-alert…）。
推播是這個專案的核心價值，統一控制權是必要的。

方向 D：技能健康、使用分析與試跑 P2

P2

統一健康模型

/skills/health 擴充
現在只有少數技能定義 health()（可查外部資料源），大多數沒有。 改成統一模型：最近一次執行成敗、連續失敗次數、連續失敗的錯誤訊息、資料源最後成功時間。
metrics 已有 skill_exec_total{skill,result}；skill 失敗也會進死信（kind: skill:<id>）。
「哪個技能最近壞掉」一眼可見，而不是翻 log 或死信。
P2

使用分析

/skills 卡片
每張技能卡顯示：近 7 日呼叫次數、失敗率、最後使用時間。並可依「從沒被用過」排序，讓清單自己浮出冗餘技能。
counter 已在記錄，只差呈現。
技能清單自己會告訴你哪些該留、哪些是死碼。
P2

技能試跑

/skills 卡片 → 試跑
在技能卡上直接打一則訊息，只看輸出不實際發送（沿用規則模擬器的比對結果 + 技能本身的輸出預覽）。
規則模擬器已能回答「會不會被觸發、為什麼」；缺的是「觸發後會回什麼」。
調參（關鍵字、時間區段、格式）不必真的在群組裡測。

方向 E：技能版本、更新與回滾 P3

P3

技能版本記錄

安裝流程
安裝前備份現有版本（data/skills/<id>.bak），skill.json 帶 version 與 api， 升級失敗可一鍵回滾。目前 installZip 是直接覆蓋，沒有版本概念。
已有 api 版本欄位可延伸；install.ts 已能擋下「需要更新主機」的技能。
技能升級有安全感；壞了能回到上一版。
P3

技能庫自動比對更新

library/ + /skills/install
技能庫現在是靜態產物，技能改了要人工重新下載。可讓 /skills 頁比對技能庫的 manifest 版本，標示「可更新」，並支援直接升級。
library 由 scripts/build-library.mjs 產生，zip 已帶 version／api。
技能生態從「手動搬檔」變成可持續分發。

方向 F：技能之間可以組合 P4

P4

技能依賴與複合查詢

技能框架
現在只有 AI 技能能呼叫工具（天氣／股價／匯率 3 個），一般技能彼此不能呼叫。 開放「技能依賴」後可組出複合技能：出門包＝天氣＋公車到站＋匯率；投資組合檢視＝stock＋price-alert。
同一份資料源常被多個技能各自抓（天氣被 weather／morning／typhoon／ai 各抓一次）。
技能從「各自的小工具」變成「可組合的能力」，也順手解決重複抓資料的浪費。

建議執行順序 Recommended Order

順位項目理由規模
1P0 修 bug（最長匹配＋衝突偵測＋裁決＋測試）兩者都會直接影響日常使用（「換算」回兩次、「倒數計時」觸發不了）；修法乾淨、可用既有模擬器當第二驗證點小
2P1 統一排程中心13 個技能共用同一套 scheduler，資料都已齊；是技能變多後最缺的一塊拼圖中
3P2 健康與分析（統一健康模型 → 使用分析 → 試跑）資料已存在，只差呈現；試跑能直接加速前面所有技能的調參中
4P3 版本與更新技能生態要能持續分發才有意義；已有 api 版本欄位可延伸中
5P4 技能組合架構改動最大（技能間呼叫與資料源共用），等前面把管理面做穩再談大
若只做一件事：做 P0 的「最長匹配優先 + 啟用時衝突偵測」。 它同時修掉兩個真 bug，而且不新增任何介面——純比對邏輯的修正，風險最低、收益最直接。

風險與不做清單 Risks & Non-Goals

動 dispatch 比對邏輯的風險：會影響所有技能的觸發行為（53 個）。 緩解：比對函式維持純函式、真實管線與規則模擬器共用、補矩陣測試； 並在改動後用模擬器比對 53 個技能既有觸發結果（改前 vs 改後 diff）作為額外保險。
這一輪明確不做：2FA／多管理員（等你真的需要多人共用再做）、技能沙箱（本專案定位是單人自用）、 衛星雲圖（CWA 路徑全 404）、QR 解碼、WhatsApp／Teams／Discord 的 AI 視覺（vision 目前只接 LINE＋Telegram）。
已完成的基礎（可安心疊加）：技能以 @lw/* 別名自包含（可外部分享）、Coverage gate（43.3%／門檻 35%）、 lint 0 errors、584 項測試、稽核紀錄＋CSV、每日營運摘要、平台連線測試、統一排程的底層（scheduler + cron + 持久化）。
