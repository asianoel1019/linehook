結論摘要 Executive Summary

這個專案的架構判斷是正確的：IMessagingService 抽象層、messaging/dispatch.ts 的共用收訊管線， 以及把技能／排程／佇列從 LINE 完全抽離，是多 IM 轉型最關鍵也最難回頭的一步，做得很紮實。 38 個技能、zip 熱安裝、三種並存的 webhook 驗證機制、per-platform 切換 UI，都是相當有厚度的功能。

但目前專案處於「功能已跑得很遠，工程防護還停在 MVP」的狀態。本次掃描確認了幾個結構性問題， 它們不是零星 bug，而是會隨著平台數、技能的成長而放大：

最關鍵的一點：所有安全邊界都建立在「只有一位管理員會好好操作」這個假設上，而這個假設沒有被任何機制強制。 安裝一個 zip 技能＝在主進程取得任意程式碼執行（可讀 process.env 內所有密鑰）； LLM 技能對任何能傳訊息的人開放、無白名單，且 summarize 可被用來做 SSRF； settings.json 明文存所有密鑰、檔案權限 0644，並且整份回傳給瀏覽器。 這些都是「架構已就位、但缺一道閘門」的情況，補起來成本不高，但順序不能晚。
第二點：資料流的「末端」是空的。 進資料有持久化、統計有 JSONL，但去路沒有——永久性失敗的訊息只寫一行 log 就消失（queue.ts:85-86）， 失敗的排程訊息會被刪除（scheduler.ts:349），收訊重送完全沒有去重（update_id／wamid 都已解析出來卻丟棄）， 訊息紀錄模組在結構上沒有任何刪除函式。也就是說，出問題時你會看到「成功率 97%」，但不知道是哪 3%。
第三點：可維護性即將成為瓶頸。 server.ts 已達 4,030 行，其中 63.7% 是 inline HTML/CSS/JS 字串； 單一 renderSettingsHtml() 就 790 行，是整個路由層（670 行）的 1.2 倍。 這同時卡住三件事：無法做 CSP、沒有測試覆蓋率、沒有 lint。

A ・ 可靠性與資料完整性 Reliability & Data Integrity

共 8 項：3 項 P0、3 項 P1、2 項 P2。本類是全報告中最直接造成資料遺失的部分。

A1

收訊完全沒有去重 — 平台重送會重複觸發

P0已實作M

Telegram、Meta、Bot Connector 在未收到 2xx 或逾時時都會重投同一則訊息。三個接收端的識別碼都被解析出來了，卻沒有人用。

證據 telegram/client.ts:288 只做 typeof update.update_id !== "number" 型別檢查即丟棄； whatsapp/client.ts:59-67 宣告了 msg.id（wamid）但 normalizeWhatsAppWebhook（:79-103）只讀 from／text； teams/client.ts:36 的 Activity.id 同樣未讀。LINE 端（line/client.ts:641-670）與 Baileys 端（web-client.ts:221-257）同樣未用 message.id／msg.key.id。
  • 重複觸發 auto-reply（triggerMode:"any"，auto-reply/index.ts:65）→ 回覆兩次
  • !send 會真的再送一次訊息給收件人（dispatch.ts:326-335）
  • 轉發規則重複轉發（dispatch.ts:271-273）、訊息紀錄重複、統計雙計
  • 現有 auto-reply 的冷卻（10 秒、以 chat 為 key）不是去重：會連合法訊息一起吞掉，且 cooldownSec=0 時完全失效
  • 全專案唯一的去重是出站的 X-Idempotency-Key，且屬 opt-in
已實作（2026-10-05）：新增 messaging/dedup.ts（24h ring）；5 平台正規化函式補 messageId；dispatchIncoming 單點檢查。測試：reliability.test.ts。
建立平台無關的 InboundDeduper：以 update_id／wamid／activity.id／message.id 為 key，TTL 建議 24h。可沿用 middleware/hmac.ts:10-26 現有的 ring + 定期 GC 寫法，無需新設計。
A2

先回 200 再處理 → 崩潰時靜默丟失收訊

P0已實作M

三個接收端都是 res.json({ok:true}) 之後才 void …handleIncoming()。這段視窗內若行程崩潰，平台已收到 200 不會重送，訊息就沒了。

證據 webhook/server.ts:3926-3927（Telegram）、:3974-3975（WhatsApp）、:3996-3997（Teams）； index.ts:20-35 的 installProcessGuards() 對任何 unhandledRejection 直接 process.exit(1)，使這個視窗不是理論值。
  • 與 A1 是同一機制的兩面：該收的不收、不該收的收
  • 最低成本修法：落地一份 data/inbound-queue.jsonl，先寫盤再回 200，背景 worker 消化後才刪
  • 完整版本：待 A6 統一儲存層後改為 inbox pattern，並在 /dashboard 顯示待處理數
已實作（2026-10-05）：新增 messaging/inbox.ts；TG／WA／Teams 三接收路由先寫盤（data/inbound-queue.jsonl）再回 200；開機回報未消化筆數。完整 replay 待 A6。
訊息可靠度從「盡力」提升到「至少一次」，與 A1 一起構成正確的 exactly-once 語意。
A3

A4

排程缺 misfire（錯過補發）策略

P1已實作S

行程重啟時若排程時間已過（例如伺服器中斷 6 小時），該次推送會被靜默跳過，使用者不會知道漏了一筆。

證據line/scheduler.ts:316-353 只處理 runAt <= now 者，恢復時不檢查落後多遠，也無任何紀錄。
  • 三選一策略：skip（現況）／fire-once（補一次）／catch-up（補全部，上限 N 次）
  • 存成 per-job 欄位，預設 skip 以維持行為相容，並在 /console 顯示「已跳過 N 次」
已實作（2026-10-05）：load() 保留 24h 內過期一次性任務並立即補發；超期寫死信後丟棄＋warn。
到價通知、晨報這類「錯過即失去意義」的技能不會因維運動作而漏發。

  • 資料源快取與健康檢查由框架統一處理（解決 A7、A8）
