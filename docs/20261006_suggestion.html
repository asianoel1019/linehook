1.2 仍未完成的關鍵缺口

最大的單一風險仍然是技能執行環境。 skills/loader.ts:34 對安裝的 zip 技能仍直接 import()，且 install.ts:116-124 只讀 id/name/version/description， 沒有權限 manifest、簽章、或沙箱。目前的防護只有 allowedUsers 白名單與速率限制。
第二大缺口是互動式訊息。 所有出站訊息都是單向的 text/media/flex/location，SendInput（messaging/types.ts:44-56）沒有 action 欄位。 這限制了「通知 → 使用者決策 → 動作」的完整閉環，也是各平台最常被使用者期待的能力。
第三是 AI 的「只能說、不能做」。 LLM 目前只能回覆文字，無法呼叫技能（工具呼叫）、無法存取知識庫（RAG）、無法串流回覆。 38 個技能已各自實作 run()，但 LLM 無法把它們當作工具來呼叫。

A ・ 互動式訊息 Interactive Messaging

共 5 項：1 項 P0、1 項 P1、3 項 P2。這是目前產品體感最大的缺口——所有訊息都是單向的，使用者只能看、不能點。

A1

互動式訊息元件（按鈕、快速回覆、選單）

P0L

擴充 SendInput 支援互動元件，讓「通知 → 使用者決策 → 動作」形成閉環。目前 messaging/types.ts:44-56 的 SendInput 只有 text/media/sticker/location/flex，沒有任何 action 欄位。

各平台現況 LINE Official：rich menu + quick reply（line-official/client.ts 已有 reply token 優化 :35-36）；
Telegram：inline keyboard（inline_keyboard 回傳 callback_query）；
Discord：components（button/select menu，Gateway 已連 :33-35）；
Teams：Adaptive Card Action.Submit（flexToAdaptiveCard 已有框架）；
WhatsApp Cloud：interactive buttons（interactive 欄位）；
WhatsApp Web：無官方支援（降級為編號清單）。
  • SendInput 加 actions?: ActionItem[]（{id, label, type: "button"|"url"|"postback"}）；各 adapter 自行降級
  • IncomingMessage 加 actionId? 與 actionValue?；dispatch.ts 可將 actionId 視為指令觸發
  • 技能可透過 ctx.reply() 的第三參數附上互動元件（如「立即訂購」「稍後提醒」）
  • 搭配 capabilities.ts 的能力矩陣，UI 在送訊前提示「此平台不支援按鈕，將以文字替代」
  • 後端收到 callback_query（Telegram）／interaction（Discord）／postback（LINE）時正規化為 IncomingMessage 進入共用 dispatch
讓到價通知可以「一鍵訂購」、讓問卷可以「點選而非打字」、讓確認操作可以在聊天中完成——這是 IM bot 從「看板」變成「工具」的關鍵一步。

現況 line-official/client.ts 可呼叫 POST /v2/bot/user/all/richmenu（設定全域 rich menu）；
Telegram 的 ReplyKeyboardMarkup / InlineKeyboardMarkup 均未使用（telegram/client.ts 的 sendMessage 只傳 text）；
38 個技能各有觸發詞，但使用者必須「記得」才能用。
  • 在 /skills 頁提供「常駐選單編輯器」：選取技能 → 拖入 3×2 或 2×3 網格 → 一鍵發佈到 LINE rich menu / Telegram reply keyboard
  • 選單動作：觸發技能（帶預設參數）、傳文字訊息、開啟 URL、回傳 actionId（配合 A1）
  • 選單配置存在 settings.json 的 richMenus 陣列，支援多組（依 chat 類型切換）
  • 與 K2（統一收件匣）的「快捷動作」共用同一套 actionId 機制
把「38 個技能」從「需要記住的命令」變成「可見的選單」，大幅降低使用門檻。

A4

對話式問答流程（多輪表單）

P2L

目前的技能是「一問一答」。但許多情境需要多輪互動（例如訂票：出發地 → 目的地 → 日期 → 確認）。這需要一個「對話狀態機」來暫存上下文。

現況 SkillContext（skills/types.ts:19-42）的 taskState 可存 per-chat 狀態（saveState），但這是「排程任務」的狀態，不是「對話流程」的狀態；
llm.ts:176 的 memory Map 是 LLM 對話歷史，也不是流程狀態；
目前沒有任何「等待使用者下一個輸入」的機制——每則訊息都是獨立的。
  • 新增 SkillContext.startFlow(flowId, steps, timeout)：宣告一組「步驟 → 問題 → 驗證 → 暫存」的流程
  • 後續訊息若在流程中，先走流程處理（而非觸發新技能），直到流程完成或逾時
  • 流程狀態持久化到 Store（flows 表），重啟後恢復
  • 與 A1 的互動元件結合：每步驟可附上「快速回覆」按鈕，讓使用者點選而非打字
讓技能從「一次性查詢」升級為「引導式對話」，可支援訂票、問卷、設定精靈等複雜場景。

P2M

四個主要平台都支援語音訊息，但目前 IncomingMessage 只處理 text。語音 → 文字（STT）→ LLM 處理 → 文字/語音回覆是自然的下一步。

現況 messaging/types.ts:28 的 IncomingMessage 只有 text 欄位；
各 adapter 的正規化函式（normalizeTelegramUpdate 等）只提取文字，忽略語音/音訊訊息；
LINE Official 已支援 audio 訊息型別（line-official/client.ts:601 有 sticker 降級但 audio 未處理）。
  • IncomingMessage 加 mediaType?: "audio"|"image"|"video" 與 mediaUrl?
  • STT 整合：OpenAI Whisper API / Google Speech-to-Text / 本地 faster-whisper（可設定）
  • 語音訊息 → STT → 走既有 dispatch 管線（可觸發技能或 LLM）→ 回覆可選擇語音或文字
  • 與 B4（多模態）共用「多媒體 → LLM」的管線
對行動使用者而言，語音是最自然的輸入方式；結合 LLM 後可實現「口述訂票」等場景。

B ・ AI 能力升級 AI Capabilities

共 7 項：1 項 P0、3 項 P1、3 項 P2。LLM 目前只能聊天、不能行動；有 38 個技能但 LLM 呼叫不到它們。

B1

LLM 工具呼叫（技能成為 LLM 的工具）

P0XL

這是目前最大的 AI 能力落差。38 個技能各有 run()，但 LLM 無法把它們當作工具來呼叫——使用者必須「記得」觸發詞，而不是自然地問「明天去高雄的火車幾點」。

現況 skills/llm.ts:75-101 的 openaiCompatChat 只發送 messages[]，沒有 tools 或 functions 欄位；
Gemini 的 geminiChat（llm.ts:110-155）同樣無工具定義；
SkillDefinition（types.ts:116-155）有 run()、defaultTrigger、usage（用法範例），但沒有 toolSchema（OpenAI function calling 的 JSON Schema）；
dispatch.ts:139-233 的 runSkills 是「觸發詞比對 → 執行」，不是「LLM 決定呼叫」。
  • SkillDefinition 加 toolSchema?: {name, description, parameters}（OpenAI function calling JSON Schema）與 runTool?(args): Promise<string>
  • 在 llm.ts 的 openaiCompatChat 加 tools 欄位；收到 tool_calls 回應時，執行對應的 runTool() 並把結果回傳給 LLM 產生最終回覆
  • Gemini 的 functionDeclarations 也要支援（llm.ts:110-155 的 geminiChat）
  • 預設把「有 toolSchema 的技能」註冊為工具；ai 技能可設定 toolMode: "auto" | "manual"（auto = 允許 LLM 自行決定，manual = 只用指定工具）
  • 工具呼叫的權限：沿用 allowedUsers（dispatch.ts:185-190），LLM 只能呼叫使用者有權限的工具
  • 記錄工具呼叫次數與成本（llm_tokens_total 已有，加 tool_calls_total）
使用者可以自然地問「明天去高雄的火車」「現在台北天氣」「比特幣多少錢」，LLM 自動選擇正確的技能並回覆——這是「助理」與「聊天機器人」的分水嶺。預估影響：38 個技能從「分散的觸發詞」變成「統一的 AI 工具箱」。
B2

RAG 知識庫（文件上傳 + 向量檢索）

P1L

讓使用者上傳自己的文件（PDF、txt、md），LLM 在回答時可檢索這些文件作為上下文。這是「通用 AI」與「你的 AI」的差別。

現況 skills/llm.ts:176 的 memory Map 只存對話歷史（ChatMessage[]），不含文件；
POST /settings/upload（server.ts:3752）已可上傳檔案到 data/uploads/，但沒有任何「讀取 → 分塊 → 向量化」的管線；
skills/summarize/index.ts 可抓取網頁內容（已加入 blockPrivate: true），但不能處理本地文件。
  • 新增 src/knowledge/ 模組：ingest()（讀文件 → 分塊 → 向量化）與 search()（查詢向量庫 → 回傳 top-k）
  • 向量庫：零依賴方案用 SQLite 的 vec0 擴充（Node 22+ 的 node:sqlite 已支援）或純 JS cosine similarity（文件量小時夠用）
  • Embedding：OpenAI text-embedding-3-small / Ollama nomic-embed-text（可設定，沿用現有 LLM provider 設定）
  • 在 ai 技能的 system prompt 中注入「相關文件片段」，並標註來源（檔案名、頁碼）
  • 管理 UI：/skills 加「知識庫」分頁：上傳、列表、刪除、重新索引
  • 與 data/uploads/ 的清理策略整合（I2 已有 pruneUploads()）
讓 bot 變成「讀過你文件的助理」——上傳公司規章、產品手冊、FAQ，即可在聊天中查詢。
B3

串流回覆與輸入中指示

P1M

LLM 回覆目前是一次性送出。長回答期間使用者看不到任何狀態，體感像「卡住了」。串流回覆是 LLM 體驗的基本盤。

現況 llm.ts:75-101 的 openaiCompatChat 使用 stream: false（預設），不讀取 SSE 流；
SkillContext.reply() 是「一次送出完整字串」；
各平台的串流能力：Telegram 可 editMessageText 逐段更新（已有 sendMessage），LINE Official 可用 reply 後再 push 追加，Teams 可用 typing activity，Discord 可用 ephemeral 更新；
messaging/text.ts 的 chunkReplyText 已有切段機制（replyMaxChars），但只用於「超過上限後分段」，不是串流。
  • llm.ts 加 stream: true 路徑：接收 SSE，每收到一個 chunk 就回調 onChunk(text)
  • SkillContext 加 replyStream(onChunk)：回傳一個「逐段更新」的 handle
  • 各 adapter 實作 streamUpdate(handle, text)：Telegram 用 editMessageText（每 500ms 更新一次）、LINE 用 push 追加、Teams 用 typing + push
  • 不支援串流的平台自動降級為「一次性回覆」
  • 先顯示「思考中…」佔位（SendInput 的 typing: true，配合 A1 的 SendInput 擴充）
把 LLM 回覆從「等待 → 一整段出現」變成「逐步出現」，大幅改善感知速度。Telegram 的 editMessageText 串流是最容易實作且效果最好的。
B4

多模態（圖片理解）

P2M

使用者傳圖片時（截圖、文件、照片），LLM 可以「看到」並理解。目前圖片訊息被忽略。

現況 IncomingMessage 只有 text；各 adapter 的正規化忽略圖片；
llm.ts 的 ChatMessage 只有 role + content（字串），不支援 image_url；
OpenAI GPT-4o、Gemini 1.5 Pro、Ollama LLaVA 均支援圖片輸入，但未被使用。
  • ChatMessage 的 content 改為 string | ContentPart[]（{type:"text"|"image_url", ...}）
  • IncomingMessage 加 mediaUrl?（A5 一併）；ai 技能收到圖片時下載並傳給 LLM
  • 支援模式：GPT-4o（base64 image）、Gemini（inline_data）、Ollama LLaVA（base64）
  • 隱私：圖片僅在 LLM 處理時暫存，處理後刪除（或依保留政策）
「幫我看這張截圖上的錯誤訊息」「這張發票的金額是多少」——圖片理解是 IM 場景中最自然的 AI 入口。

B6

Prompt 版本管理與 A/B 測試

P2M

目前 prompt 是硬編在技能程式碼裡（如 summarize/index.ts:11 的 DEFAULT_SYSTEM_PROMPT）。無法在不改程式碼的情況下調整 prompt，也無法比較不同版本的效果。

現況 ai 技能的 systemPrompt 可由使用者在 /skills 設定（ai/index.ts:75），但這是「使用者自訂」而非「版本管理」；
summarize 的 DEFAULT_SYSTEM_PROMPT 硬編在程式碼；
無 prompt 版本、無 A/B 測試、無效果衡量。
  • 把 prompt 抽成可管理的資源：prompts 陣列（{id, name, content, version, tags}）存在 settings.json 或 Store
  • 技能可引用 prompt id（而非硬編），ai / summarize 等改為 promptRef: "summarize-v2"
  • A/B 測試：設定「分流比例」（如 50% 用 v1、50% 用 v2），記錄各自的滿意度（使用者回覆「有用/沒用」或隱含指標如後續是否重問）
  • 在 /skills 的 prompt 編輯器支援「版本歷史」與「回滾」
讓 prompt 優化成為「資料驅動的迭代」而非「憑感覺改」。
B7

對話記憶管理（per-chat、可編輯、可持久化）

P2M

目前 LLM 記憶是 skills/llm.ts:176 的 Map<string, ChatMessage[]>——不持久化、無總量上限、無管理 UI。使用者無法「刪除某段對話」或「編輯記憶」。

現況 llm.ts:182-191 pushHistory() 只做 per-chat 的 front-trim（keepTurns 預設 6）；
重啟後所有記憶消失；data/messages.jsonl 有記錄但 LLM 不會從中恢復；
ai/index.ts:62-66 有 清除記憶|忘記|reset 指令，但只能清單一 chat；
無「編輯記憶」（如「你叫阿寶」→ 永遠記住）。
  • 記憶持久化到 Store（memory 表：chatId, role, content, tokens, savedAt），重啟後恢復
  • 加總量上限（LRU 淘汰）與 TTL（如 7 天未互動則清除）
  • 管理 UI：/messages 加「記憶」分頁：查看某 chat 的記憶、手動刪除、編輯
  • 「長期記憶」：使用者可說「記住：我喜歡靠窗的座位」→ 寫入持久記憶（不隨 keepTurns 淘汰）
  • 隱私：記憶可被使用者在聊天中刪除（forget me 指令），也可在 UI 刪除

C ・ 技能生態系 Skill Ecosystem

共 5 項：1 項 P0、2 項 P1、2 項 P2。38 個技能已是最有價值的資產，但分享、更新、安全仍未解。

C1

技能沙箱與權限 manifest

P0XL

這是最大的安全缺口。安裝的 zip 技能仍是在主進程中直接 import() 的任意程式碼。需要至少「宣告式權限 + 靜態掃描」作為第一道防線。

現況 skills/loader.ts:34 await import(pathToFileURL(target).href)——無沙箱；
skills/install.ts:116-124 只讀 skill.json 的 id/name/version/description，沒有 permissions 欄位；
skills/validate.ts 只驗 config 值（required/pattern/min/max），不驗程式碼；
現有防護：per-skill allowedUsers（dispatch.ts:185-190）+ rate limit（dispatch.ts:22-28）。這是「授權」層面的防護，不是「程式碼」層面的。
  • 第一步（低成本）：skill.json 加 permissions: {fs: string[], net: string[], env: string[]}；安裝時顯示權限清單並要求確認；/skills 卡片顯示權限標籤
  • 第二步：安裝時靜態掃描（阻擋 child_process、process.env、動態 import、eval、Function()），掃描結果存入 install.ts 的安裝紀錄
  • 第三步：執行期沙箱——node:vm 或 worker_threads 搭配受限的 require；官方 38 個技能維持 in-process（可信），僅對使用者安裝的技能套用
  • 第四步：簽章驗證——skill.json 加 signature（作者金鑰簽章 + SHA-256 checksum），安裝前驗證
即使只做第一二步，對「下載來路不明的技能 zip」這個真實使用情境就已是數量級的提升。也是「技能市集」（C3）的前置條件。
C2

技能版本管理與回滾

P1M

目前安裝/卸載是「刪除目錄 + 重新載入」。更新技能等同「刪掉再裝」，若新版有 bug 就只能手動裝回舊版。

現況 server.ts:773 POST /skills/install 直接覆蓋 data/skills/<id>/；
server.ts:786 POST /skills/uninstall 直接 rm -rf；
skill.json 有 version 欄位（install.ts:66-123 讀取），但沒有版本歷史、無比較、無回滾。
  • 更新前把舊目錄 rename 為 .bak（或複製到 data/skills-versions/<id>/<version>/）
  • /skills 加「回滾到上一版」按鈕（呼叫 rename back）
  • 安裝/更新失敗（載入拋錯）時自動回滾，並在 UI 顯示原因
  • skill.json 加 previousVersions 或用獨立的 versions.jsonl 記錄安裝歷史
  • 與 C1 的簽章配合：回滾時也驗證舊版簽章
讓「技能更新」從高風險操作變成可逆操作。
C3

技能市集（搜尋、評分、簽章）

P1L

library/index.html 已是完整的靜態技能庫（37 個 zip + 分類篩選），但它與 /skills 管理頁是兩個互不相通的世界。把市集接進產品，降低技能分發成本。

/skills 頁只有「上傳 zip」與「卸載」，沒有瀏覽市集的入口；

  • 在 /skills 加「技能市集」分頁：直接讀 library/ 的 manifest（而非解析 HTML），顯示分類/關鍵字搜尋/已安裝標記/一鍵安裝
  • 顯示每個技能的權限需求（C1）與最後更新時間、版本、下載次數
  • 評分系統：使用者可給予 1-5 星 + 簡評；本機的 skill_exec_total 作為「使用頻率」指標
  • 簽章：官方 38 個技能由專案金鑰簽章（skill.json.signature）；第三方技能顯示「未簽章」警示

把已做好的靜態頁接進產品，並加上安全簽章——這是 38 個技能價值的放大器。
C4

可組合資料源 + 通用告警技能

P2L

38 個技能中約一半是「打某個 API → 格式化 → 回覆」。price-alert／rss／morning 已經是「資料源 + 條件 + 推播」的形态，但各自實作。把這個形态抽成框架，新增技能的成本會大幅下降。

現況 skills/price-alert/index.ts、skills/rss/index.ts、skills/morning/index.ts 各自定義「資料取得 + 條件判斷 + 推播」；

skills/watch.ts 已有 ctx.watch() 週期任務機制，可被框架使用。
  • 抽象 DataSource（fetch(): Promise<T> + normalize(): T）與 AlertRule（condition(T): boolean + notify(T): SendInput）
  • 把 price-alert／rss／morning／outage／quake 遷移作為示範
  • 通用 alert 技能：使用者只需選資料源 + 條件（價格高於 X／關鍵字出現／值變動幅度）+ 推播目標，不需寫程式
  • 資料源快取與健康檢查由框架統一處理（解決 A7、A8 的殘餘問題）
  • 資料源宣告自己適用的 locale/區域，不適用時明確提示
讓技能數量能持續成長而不失控——新增一個「外匯到價通知」只需要 10 行設定而非 200 行程式碼。

P2M

現況 tests/new-skills.test.ts 直接 import 各技能的內部 helper 並斷言；

  • 提供 fetchStub（依 URL pattern 回傳 fixture）取代「只測離線拒絕分支」
  • 在 /skills 的技能卡上顯示「健康度」= 該技能是否有測試覆蓋
  • 與 C1 的 manifest 一併提供 testCommand 欄位

D ・ 多使用者與協作 Multi-User & Collaboration

共 5 項：1 項 P0、2 項 P1、2 項 P2。目前只有單一管理帳號；團隊使用時「誰能做什麼」必須分開。

D1

多使用者帳號與角色

P0L

目前只有單一 STATUS_USER / AUTH_PATH。若這個 bot 要服務一個小團隊，「誰能看到訊息、誰能改設定、誰能裝技能」必須分開。

現況 middleware/session.ts:45-47 currentUser() 只回傳一個 identity，無 user table；
audit.ts 已記錄 user 欄位（:28-45），但只有一個使用者；
Token-level scopes 已有（read|send|admin，config.ts:180-187），但這些是 API token 的 scope，不是使用者角色。
  • 帳號資料模型：users 陣列（{id, username, passwordHash, role, enabled}）存在 data/users.json 或 Store
  • 角色模型：owner（全部）/ admin（設定+技能+備份）/ operator（測試送+排程+死信重送）/ viewer（只讀 dashboard+messages）
  • 權限檢查從單一 requireSessionOrApi(scope) 擴充為 requireRole(role)；路由層級即可完成
  • 登入介面改為「選擇使用者」或輸入 username；currentUser() 回傳使用者物件
  • 與既有 audit trail（audit.ts）整合：所有操作記錄 actor username
這是「多人使用」的必要條件，也是 K1 的核心。
D2

2FA / TOTP

P1M

目前只有「帳號 + 密碼」，且密碼驗證走 .env 明文比對（session.ts:84-89，無 auth.json 時）。2FA 是保護管理介面最有效的額外防線。

現況 無 totp|otp|webauthn|2fa；
loginRateLimit（rateLimit.ts:39-53）只按 IP 限流（20次/5min），無帳號鎖定；
5 分鐘閒置登出已實作（session.ts:8 SESSION_TTL_MS），但無絕對過期時間。
  • TOTP 實作：otpauth:// URI 產生 QR（已依賴 qrcode），驗證時用 crypto 計算 TOTP（零依賴）
  • 登入流程改為兩步：密碼 → TOTP 驗證碼
  • 備用碼：產生 10 個一次性備用碼，存入 data/auth.json
  • 帳號鎖定：同一 username 連續 N 次失敗 → 指數退避 + 告警（接上 notify/alert.ts）
  • 可選：WebAuthn / passkey（更現代，但依賴較重）
在 D1（多使用者）之後，2FA 是保護 owner/admin 角色的關鍵防線。
D3

審計軌跡查詢 UI

P1M

audit.ts 已寫入 audit.jsonl（:28-45），但目前沒有任何查詢介面。「誰在什麼時候改了設定」是事故回溯的第一個問題。

現況 audit.ts 寫入 {time, ip, user, action, detail}，有輪替；
已在 server.ts:886,931,944,982,999 等敏感操作呼叫；
但無查詢 API、無 UI、無過濾。
  • 新增 GET /audit.json（admin scope）：支援時間範圍、操作類型、使用者、IP 過濾
  • 在 /dashboard 或獨立頁面顯示審計時間軸（最近 100 筆 + 分頁）
  • 保留政策：依天數自動修剪（與 pruneMessages() 併入 Store 的 prune()）
  • 與 D1 的多使用者整合：顯示「誰」做了什麼（而不只是 IP）
從「有紀錄但看不到」變成「可查詢、可過濾、可回溯」。
D4

團隊協作（共享設定、審批流程）

P2L

在 D1 的多使用者基礎上，增加「審批」概念：某些高風險操作（安裝技能、改密鑰、發佈排程）需要另一位管理員確認。

現況 所有操作都是「立即生效」，無審批流程；
audit.ts 可記錄誰做了什麼，但不能阻止任何人。
  • 審批類型：技能安裝/卸載、設定變更（密鑰類）、排程發佈、備份還原
  • 流程：operator 提交 → admin/owner 批准 → 執行；拒絕時通知提交者
  • 審批記錄存入 audit trail
  • 可設定「哪些操作需要審批」（settings.json 的 approvalRequired: string[]）
降低「一人手滑改了生產設定」的風險，適合團隊共管場景。
D5

API Key 管理增強（輪替、過期、範圍）

P2M

目前 apiTokens 已有 scope（read|send|admin）和使用統計（token-stats.ts），但缺少「輪替」與「過期」這兩個安全營運的基本能力。

現況 config.ts:180-187 apiTokens 有 name/token/scopes；
token-stats.ts 記錄 count/lastUsedAt/lastIp；
無過期時間、無自動輪替、無「建立後不可回看」的模式。
  • API token 加 expiresAt（可選）與 createdAt；過期後自動失效並在 dashboard 提示
  • 輪替：「建立新 token → 通知 → 舊 token 設定 grace period → 自動失效」的流程
  • 建立 token 時只顯示一次（之後僅顯示 token_prefix）；GET /settings.json 回傳遮罩值
  • 「最後使用時間」異常時告警（如 token 已 90 天未使用 → 建議撤銷）
讓 API token 的生命週期管理從「手動」變成「可自動化」。

E ・ 資料洞察與智慧 Data Insights & Intelligence

共 5 項：2 項 P1、3 項 P2。Store 已統一，但「從資料中得到洞見」的能力仍待開拓。

E1

統一搜尋（跨訊息、死信、審計、統計）

P1M

目前 /messages 只搜訊息（messages.ts:77-93），死信在 /console，審計無 UI。出問題時需要在多個頁面之間切換才能拼出全貌。

現況 Store 的 query() 已支援 q/chat/limit（store/types.ts:42-58），但只用於 messages 表；
deadletter 表有 summary/error 欄位但無全文搜尋；
audit.jsonl 不在 Store 中，無法 SQL 查詢。
  • 把 audit 也納入 Store（audit 表），或提供 JSONL 的全文檢索
  • 統一搜尋頁面：/search?q=<keyword>，同時搜訊息/死信/審計，結果按時間排序並標註來源
  • 支援正規式、時間範圍、平台/聊天過濾、訊息型別過濾

E2

異常偵測與主動告警

P1M

目前告警只在「已知事件」（登入失效、死信超閾值）時觸發。但「訊息量突然暴增」「某技能錯誤率飆升」「排程器停滯」這類模式變化沒有人在看。

現況 metrics.ts 已有 im_send_total/http_requests_total/scheduler_jobs 等 counter；
monitor/token.ts 的健康監控只檢查「平台是否登入」；
notify/alert.ts 的告警通道已就緒（Email + webhook + dead-man switch）；
無基線計算、無趨勢分析、無異常偵測。
  • 輕量異常偵測：每個 metric 記錄滑動平均與標準差，超過 mean + 2σ 時告警
  • 常見規則：發送失敗率 > 20%（5 分鐘窗口）、某技能錯誤次數 > N、排程器 > M 分鐘無執行、LLM 成本單日 > 基線 3 倍
  • 告警內容附帶「最近 N 分鐘的對比數據」，讓接收者能快速判斷
  • 與 /metrics 的 Prometheus 格式一致，可被 Grafana Alerting 消費（F3）
從「壞了才知道」變成「正在變壞就警告」，這是運維成熟度的質變。
E3

P2L

P2M

P2M

H1

密鑰輪替（zero-downtime）

P1M

目前所有密鑰（HMAC secret、API token、Telegram bot token、WhatsApp access token、Teams app password）都存在 settings.json，明文且無輪替機制。

現況 settings.ts:475 已設定 mode: 0o600（檔案權限已修）；
settings-crypto.ts 已有 AES-256-GCM + scrypt，但只用於匯出/匯入/備份的密碼封裝（server.ts:943,967,999），不用於磁碟上的密鑰欄位；
GET /settings.json 回傳全部密鑰給瀏覽器（settings.ts:225-240）；
無「輪替」流程、無「舊密鑰 grace period」、無「建立後不可回看」。
  • 密鑰欄位加密：settings-crypto.ts 擴用到磁碟上的密鑰欄位（encryptedSecrets 陣列 + 解密時載入）
  • GET /settings.json 回傳遮罩值（•••• + hasSecret 旗標），未修改則保留原值
  • 輪替流程：「建立新密鑰 → 通知（多通道）→ 舊密鑰 grace period（如 24h）→ 自動失效」
  • 支援「雙密鑰驗證」：新舊密鑰在 grace period 內都可通過驗證
讓密鑰洩漏的爆炸半徑從「全部失效」縮小到「一個密鑰 + 24 小時」。

現況 settings.ts:11-12 migrations 陣列為空（[]），只有格式佔位註解；

  • Store 加 schema_version 表（或 PRAGMA user_version），升級時自動套用遷移
  • 自動備份：每日/每週將 data/ + settings.json + storage.json + data/skills/ 打包（可選加密）
  • 雲端上傳：S3 / GCS / WebDAV（可設定），保留 N 份
  • 還原流程：驗證完整性 → 檢查版本 → 自動套用遷移 → 重啟
讓「按 README 升級」與「災難復原」從 checklist 變成一個按鈕。

建議執行順序 Roadmap

依「使用者價值 × 技術前置 × 風險消除」三個準則排序。每階段的項目可平行推進。

Phase 1 · 核心能力

讓 bot 從「看板」變成「工具」

建議 2–4 週 · 本階段的成果將定義產品的下一版核心體驗
  • A1 互動式訊息元件（按鈕/快速回覆/選單）— 產品體感最大的跳變
  • B1 LLM 工具呼叫（技能成為 AI 工具）— 解鎖 38 個技能的自然語言入口
  • C1 技能沙箱與權限 manifest（至少第一、二步）— 消除最大的安全缺口
  • B5 LLM 預算護欄 + 成本持久化 — 防止成本失控
  • D1 多使用者帳號與角色 — 團隊使用的基本前提
  • G3 i18n 補齊（dispatch bot 回覆優先）— 讓三語真正成立
為什麼是這個順序：A1 + B1 是產品層面最大的兩個「質變」——互動式訊息讓使用者「可以點」，工具呼叫讓 AI「可以做」。 C1 是安全前置（沒有沙箱就不該開放技能市集），D1 是協作前置，B5 是財務前置。 G3 雖然不是「功能」但直接影響使用者感受，且是純文案工作、可平行完成。
Phase 2 · 深度與智慧

從「可用」到「好用」到「聰明」

建議 4–8 週 · 在 Phase 1 的基礎上加深
  • B2 RAG 知識庫 — 變成「讀過你文件的助理」
  • B3 串流回覆 — LLM 體驗的基本盤
  • C2 技能版本管理與回滾 + C3 技能市集
  • D2 2FA/TOTP + D3 審計軌跡查詢 UI
  • E1 統一搜尋 + E2 異常偵測與主動告警
  • F1 OpenAPI + F2 Webhook 試算機 + F3 Grafana 範本
  • G1 PWA + 行動推播 + G2 無障礙
  • H1 密鑰輪替 + H2 遷移 runner + 自動備份
這一階段的特徵是「每個領域都在深化」：AI 從對話到行動（B1→B2→B3）、技能從安裝到生態（C1→C2→C3）、 營運從手動到自動（H1→H2）、開發者從讀文件到自助（F1→F2→F3）。
Phase 3 · 規模與差異化

建立護城河

無時限壓力 · 依使用者回饋決定優先序
  • A2 Rich Menu + A3 跨平台模板預覽 + A4 對話式問答流程 + A5 語音輸入
  • B4 多模態（圖片理解）+ B6 Prompt 版本管理 + B7 對話記憶管理
  • C4 可組合資料源 + C5 技能測試 harness
  • D4 團隊審批流程 + D5 API Key 輪替
  • E3 使用者行為分析 + E4 成本優化建議 + E5 GDPR
  • F4 SDK + F5 簽章測試工具
  • G4 鍵盤快捷鍵 + G5 跨平台格式轉譯
  • H3 Kubernetes Helm Chart
Phase 3 的項目多數可「隨需求加」而非「必須一次做完」。A4（對話式流程）與 C4（可組合資料源）是最可能帶動 新一波使用者成長的兩項，建議優先投入。G5（格式轉譯）則在使用者開始跨平台使用時才會感受到痛點。
